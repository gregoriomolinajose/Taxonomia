# S47.3 Retrospective: Database Batch Dispatch

## Summary
- **Story ID:** S47.3
- **Dates:** 2026-04-28
- **Estimated vs Actual:** 30 mins vs 20 mins.

## What Went Well
- La integración con `_dispatchChunks` fue sencilla y directa. La abstracción original que construimos para manejar timeouts (lotes síncronos sobre JS) ha demostrado ser sumamente robusta al ingerir este nuevo pipeline de Capacidades sin necesidad de reescribir la persistencia.

## What to Improve
- Inicialmente `DataEngine_ETL_Capacidades` quedó acoplado fuertemente a `window.UI_ETL_Modal`. Aunque solucionamos esto mediante callbacks parametrizados durante la revisión de calidad, sería útil definir un estándar de "Interfaces Visuales" (`EventEmitters`) para futuros parsers.

## Heutagogical Checkpoint
1. **What did you learn?** Reutilizar los mecanismos internos (como `showResults` y `updateProgress` a través de callbacks) permite que el usuario no note que hay un script completamente diferente por debajo.
2. **What would you change about the process?** Mantener el enfoque de diseño orientado a interfaces desde la Fase S47.1, donde se inyectaron directamente las variables globales de UI.
3. **Are there improvements for the framework?** La validación manual final debe estipularse claramente en el scope para probar inserciones destructivas (Bulk).
4. **What are you more capable of now?** Hemos cerrado exitosamente una épica completa utilizando las tres fases del patrón RaiSE, manteniendo separación de responsabilidades y logrando un parser nativo `xlsx` sin colapsar el entorno `GAS`.

## Patterns Added/Reinforced
- Reforzado patrón de **Dependency Injection** rudimentaria para la capa de UI.

## Hotfix (28-04-2026): Idempotencia y Reportes
Durante las pruebas de usuario posteriores a la entrega S47.3, se detectaron y resolvieron dos incidentes críticos de estabilización:
1. **Idempotencia de Grafos Topológicos:** El motor ETL insertaba directamente en la base de datos los identificadores temporales topológicos (`M|||...`) en lugar de convertirlos a UUIDs reales (`CAPA-XXX`). Esto corrompía la integridad. Se implementó una pre-resolución asíncrona: El motor hace un `DataAPI.call('list', 'Capacidad')` previo y busca si el `path_completo_es` ya existe. Si existe, usa el UUID existente (actualización); si no, genera uno nuevo válido.
2. **Read-Only Feedback:** Debido a la restricción de Google Workspace que requiere un OAuth Scope `drive.readonly` para leer archivos arbitrarios, el motor no podía "marcar" las columnas de estado en el Excel del usuario. Como mitigación, se implementó la retención de un `accumulatedFeedback` inyectado hasta el modal del UI, dotándolo con un botón nativo para descargar un reporte CSV con el detalle exacto de las filas duplicadas/fallidas.
