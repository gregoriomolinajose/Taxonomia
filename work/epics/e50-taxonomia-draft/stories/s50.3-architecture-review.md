### Recommended (simplify before next cycle)
- **`UI_SubgridBuilder.client.js` (L89) y `UI_Component_RelationBuilder.client.js` (L106): [H9 - Semantic Duplication]** 
  La lógica para extraer el `contextId` (verificar si la entidad es "Taxonomia" o si el `ion-modal` activo tiene el dataset `isDraft`) se ha duplicado exactamente en ambos constructores.
  - *Proportionality concern:* Si en el futuro cambiamos la forma en que se identifica un borrador activo en la UI, tendríamos que buscar y cambiar ambos archivos.
  - *Concrete simplification:* Extraer esta lógica a un utilitario centralizado. Como la épica aún está en curso y esto no detiene la completitud semántica de la UI, se recomienda extraerlo en una historia de _refactor_ posterior (ej. creando `window.UI_FormUtils.extractDraftContext()`) o resolverlo antes de cerrar la épica.

### Questions (require human judgment)
- **`UI_Factory_Searchables.client.js`: [H6 - Indirection Depth]**
  Para pasar el `contextId` a `<tx-searchable>`, tuvimos que pasarlo a través de `visualTokens` desde `RelationBuilder`. ¿Consideras que `visualTokens` es el "namespace" semánticamente correcto para inyectar IDs de contexto de base de datos? Una alternativa sería pasarlo como un argumento directo al Factory, pero cambiaría la firma de una API pública (`buildSearchableMulti`). Al usar `visualTokens`, evitamos refactorizaciones profundas.

### Observations (patterns noted)
- **Top-Down Prop Drilling vs Global State:** La decisión de usar atributos del DOM (`context-id`) en los Web Components (`tx-searchable`) respeta el paradigma "Pure Nodal" y previene problemas de hidratación cruzada (ej. si hubieran múltiples wizards abiertos en pestañas/iframes).
