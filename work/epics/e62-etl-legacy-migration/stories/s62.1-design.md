# Story Design: S62.1

## Problem & Value
**Problem**: The legacy ETL client scripts (`DataEngine_ETL.client.js`) contain critical business logic for validating `Persona` email domains and triggering Workspace Sync, which blocks their deprecation.
**Value**: Moving this logic to the backend enables the safe removal of legacy frontend ETL code, ensures data integrity across all entry points, and improves architectural decoupling.

## Approach
- **Validation**: Implement an interceptor (e.g., `EnforceAllowedDomains`) in `src/Business_Interceptors.js` for the `Persona` entity. It will read `CONFIG.ALLOWED_DOMAINS` (via `API_Auth` or `ENV_CONFIG` in backend context) and reject any payload where the email domain does not match.
- **Auto-Sync Chaining**: Update the `src/Job_Worker.js` or `Engine_ETL.js` job completion phase. If the completed job processed `Persona` entities successfully, automatically push a new job for Workspace Sync (`Job_WorkspaceSync`) into the queue.
- **Missing-Entity Strategy**: Invalid domains are treated as hard validation failures. The mutation for that specific `Persona` is rejected, and an error is logged. (No partial success or silent drops for invalid domains).
- **Value Preservation Gate**: The domain validation preserves the core domain intelligence of restricting platform access to authorized company domains. The Workspace Sync preserves the automated provisioning/deprovisioning topology rules.

## Examples
### Scenario 1: Valid Domain Mutation
```javascript
// Input
const personaPayload = { email: "user@bancoppel.com", name: "Alice" };
// Assuming global.CONFIG.ALLOWED_DOMAINS = ['@bancoppel.com', '@coppel.com']

// Expected Output
// Interceptor allows the payload through to Engine_DB.upsert
```

### Scenario 2: Invalid Domain Mutation
```javascript
// Input
const personaPayload = { email: "user@gmail.com", name: "Bob" };
// Assuming global.CONFIG.ALLOWED_DOMAINS = ['@bancoppel.com', '@coppel.com']

// Expected Output
// Interceptor throws Error or drops the record from the batch, logging: "Domain @gmail.com is not allowed."
```

### Scenario 3: Job Chaining
```javascript
// Input
// Job_Worker finishes processing an ETL job with metadata: { entity: "Persona", status: "COMPLETED" }

// Expected Output
// Job_Worker enqueues a new background job to execute Job_WorkspaceSync logic automatically.
```

## Acceptance Criteria
- **MUST**: Persona mutations (inserts/updates) are rejected by the backend if their email domain is not in `ALLOWED_DOMAINS`.
- **MUST**: When an ETL job for `Persona` completes successfully, the Workspace Sync job is automatically queued or executed.
- **MUST NOT**: The frontend client should no longer be responsible for executing Workspace Sync directly after ETL processing.
