## Execution Order
1. **Task 1** - Establishes the contract for communication between runner and reporter.
2. **Task 2** - Implements the core complex logic for chunking (highest risk).
3. **Task 3** - Wires up the reporting using the new data structures and chunking outputs.
4. **Task 4** - Validates the complete pipeline works cohesively.

**Rationale:** Building the data contract first prevents integration mismatches. The runner logic addresses the core timeout risk, so it should be implemented next. The reporter simply consumes the new behavior, and end-to-end validation ensures the user-facing outcome is achieved.

## Risks and Mitigations
- **Risk:** Background tasks may still fail unexpectedly, leaving the system in an unknown state.
  - **Mitigation:** Ensure robust exception catching around the chunk processing block to always return an `EtlResult` with an error state.
- **Risk:** Chunk size might be inappropriate for available memory.
  - **Mitigation:** Allow `chunk_size` to be configurable and provide a safe default (e.g., 5000).
