# Story Review (Retrospective): S61.4 Async Job Processing

## 1. Did we achieve the goal?
Yes. We implemented the Async Job Processing mechanism for the Google Apps Script backend. We created a Job Queue (`Job_Queue.js`) and a worker `Job_Worker.js` that uses triggers to process records in chunks, completely bypassing the 6-minute execution limit. The frontend `UI_Component_BulkImporter.client.js` was updated to enqueue jobs and poll for progress, providing immediate feedback and a smooth progress bar.

## 2. What went well?
- Utilizing `CacheService` to handle locking and chunk persistence worked beautifully.
- Decoupling the ETL extraction phase from the database processing allowed us to scale without timeouts.
- Replacing the generic `ion-loading` spinner with a custom UI overlay drastically improved the UX.

## 3. What went wrong?
- **Data Mapping Issue:** We forgot to map the human-readable headers to schema keys before sending them to the backend adapter. This caused the database to insert blank rows, creating a difficult-to-debug "ghost rows" issue.
- **Silent Failures:** The `Job_Worker` threw errors when it couldn't find a primary key, but because of how Google Sheets works, it skipped rows silently instead of bubbling up a clear error in the batch.

## 4. Learnings
- **Always Verify Mapping Early:** Ensure data extraction pipelines apply mapping transformations *before* sending payloads to the persistence layer.
- **Immediate UX Feedback:** When starting long-running async tasks, always provide immediate visual feedback. Don't rely on generic spinners that block the screen without providing context.
- **Schema Key Inference:** Always ensure the schema keys are available when doing upsert operations to avoid data loss.

## 5. Next Steps
- Implement S61.5 (DLQ UI) to visualize the errors caught by the background jobs.
- Refactor how `Job_Worker` logs failures to store them in a persistent table rather than just CacheService.
