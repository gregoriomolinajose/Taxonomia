# S61.14 Design: ETL Job Mutex Lock

## Problem & Value
**Problem**: Concurrent UI pulses and Time Triggers can fetch the same PENDING ETL job because the initial general script lock is released early. This results in the same job being processed multiple times, causing race conditions and duplicated work.
**Value**: Ensure each job is processed exactly once by adding a job-specific Cache mutex, improving stability and performance.

## Approach
Implement a cache-based Mutex within the processing loop of `Job_Worker.js`. 
- Retrieve the job from the queue.
- Check `CacheService.getScriptCache()` for the key `JOB_LOCK_ + job.jobId`.
- If the key exists, release the ScriptLock and return early: `{ debug: "job_already_processing" }`.
- If it does not exist, claim the job exclusively by putting it in the cache for 240 seconds.
- Wrap the job processing logic in a `try...finally` block.
- In the `finally` block, remove the lock from the cache.

### Components Affected
- `src/Job_Worker.js` (modify)

## Examples

**Example Execution Flow**:
1. Thread A picks up Job 123.
2. Thread A writes to cache: `JOB_LOCK_123` = `"1"` (expires in 240s).
3. Thread B picks up Job 123 (concurrent read before status updated).
4. Thread B reads cache `JOB_LOCK_123` and finds `"1"`.
5. Thread B releases the global lock and returns `{ debug: "job_already_processing" }`.
6. Thread A finishes processing Job 123.
7. Thread A removes `JOB_LOCK_123` from cache in a `finally` block.

## Acceptance Criteria
- **MUST**: Cache mutex is checked and acquired successfully before job processing begins.
- **MUST**: Lock is cleared successfully in a `finally` block after job completes or fails.
- **MUST**: Concurrent threads abort execution and return a specific debug object if they hit an existing cache lock.
