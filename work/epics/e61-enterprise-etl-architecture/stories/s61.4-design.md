# Story Design: S61.4 Async Job Processing

## Problem & Value
**Problem:** The current ETL engine processes rows synchronously in the HTTP request cycle, causing browser timeouts and GAS execution limits when processing >10,000 rows.
**Value:** Migrating to an async job queue prevents timeouts, improves user experience via progress indicators, and safely handles large data volumes in chunks.

## Approach
We will build a simple `JobQueue` on Google Sheets or a temporal store to track job status (PENDING, PROCESSING, COMPLETED, FAILED, state). 
1. **API**: Instead of running the ETL, the API enqueues a job payload and returns a JobID.
2. **Worker**: A time-driven trigger or chained trigger picks up the job and processes rows in chunks. When close to the 6-minute limit, it saves its cursor/state and schedules the next run.
3. **Frontend**: Receives the JobID and polls an endpoint (e.g. `GET /jobs/:id`) every X seconds to update a progress bar.
4. **Errors**: Failed rows are saved to a Dead Letter Queue (DLQ) structure on the backend.

## Examples

**Example 1: Enqueue Job**
```typescript
// POST /api/import
// Payload
{ data: [{...}, {...}] }

// Response
{ jobId: "job_12345", status: "PENDING" }
```

**Example 2: Poll Status**
```typescript
// GET /api/jobs/job_12345
// Response
{ 
  jobId: "job_12345", 
  status: "PROCESSING", 
  processed: 5000, 
  total: 15000,
  errors: 0 
}
```

## Acceptance Criteria
- **MUST**: Backend provides `/api/jobs/enqueue` (or adapts `/api/import`) and `/api/jobs/status`.
- **MUST**: GAS worker processes rows in chunks, stopping and re-triggering before 6 mins.
- **MUST**: Frontend polls the status endpoint without freezing the UI.
- **MUST**: Erroneous rows are pushed to DLQ array in the job state or separate sheet.
