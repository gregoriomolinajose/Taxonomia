# Story S61.13 Design

## What & Why
**Problem:** The `signals` array in `_checkCacheSignals` can grow too large and hit the CacheService 100KB limit. Additionally, `matchedRow` can be `undefined` when no match is found, which isn't explicitly clear in evaluation logs.
**Value:** Pruning the array avoids cache limit exceptions. Setting `null` ensures data integrity for ETL logs.

## Approach
- **Engine_DB.js**: In `_checkCacheSignals`, right before `cache.put`, apply a reduction over `signals` to keep only the one with the maximum `invalidated_at` for each unique pair of `entity_name` and `by_tenant`.
- **Engine_ETL.js**: When matching rows, explicitly assign `null` if the db search does not find a match.

## Examples
**Input to caching:**
`signals = [ { entity_name: 'A', by_tenant: 'T1', invalidated_at: 100 }, { entity_name: 'A', by_tenant: 'T1', invalidated_at: 200 } ]`
**Output to cache:**
`signals = [ { entity_name: 'A', by_tenant: 'T1', invalidated_at: 200 } ]`

## Acceptance Criteria
- MUST reduce the `signals` array to only the single most recent signal (largest `invalidated_at`) for each unique `entity_name` + `by_tenant` combination before caching.
- MUST explicitly assign `null` to `matchedRow` instead of `undefined` when DB search finds no match in `Engine_ETL.js`.
