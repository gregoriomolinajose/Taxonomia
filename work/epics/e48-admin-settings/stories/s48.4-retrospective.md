# Retrospective S48.4: Autorización OAuth2 (3-Legged) para Workspace Multi-Dominio

## Summary
Se implementó con éxito el flujo OAuth2 de 3 patas (3-legged) para habilitar la sincronización de perfiles de usuarios pertenecientes a dominios externos de Google Workspace (ej. `@bellfy.app`). Esto permite a Taxonomia auto-completar nombres, puestos y fotografías de colaboradores externos sin requerir Service Accounts ni configuraciones complejas en la consola de Workspace, descentralizando la delegación de permisos a través del estándar OAuth.

Además, se resolvió un bloqueo arquitectónico relacionado a las restricciones de privacidad de Google Apps Script (`USER_DEPLOYING` vs `USER_ACCESSING`), documentando el trade-off entre la visualización de la pantalla de permisos nativa de Google y la necesidad de una futura integración directa de Google Identity Services (Sign-In with Google) para la experiencia del usuario final.

## Achievements
- **Integración Librería OAuth2 Oficial:** Se inyectó la dependencia en `appsscript.json` y se conectó limpiamente con `Code.js` (`doGet` interceptor).
- **Abstracción Segura:** `Auth_OAuth2.js` consolida la autorización y preserva los *Refresh Tokens* en el `PropertiesService` por dominio (`Workspace_@dominio.com`).
- **Fail-Open Workspace Engine:** `Engine_Workspace.js` conmuta dinámicamente:
  - Si el dominio del correo coincide con la identidad principal, usa `AdminDirectory` (SDK nativo).
  - Si el dominio es externo, busca el Token en el servicio de propiedades y realiza la consulta con `UrlFetchApp` (Bearer Token).
- **Mejoras UX Administrativas:** La interfaz (`Schema_Studio_UI.html`) controla ventanas emergentes, re-renderiza el estado de los conectores tras la autorización y evita bloqueos (WSOD) con alertas nativas.
- **Protección del Dashboard:** Se eliminaron los conteos innecesarios de *Roles* y *Cargos* en la pantalla principal.
- **Validación del Muro de Google:** Descubrimiento crítico documentado sobre la restricción de Google Apps Script para ocultar correos externos bajo `USER_DEPLOYING`.

## Learnings & Technical Debt
- **[DEUDA TÉCNICA - E48-NEXT]:** Para que usuarios de múltiples dominios accedan a la aplicación sin ver la pantalla de advertencia de "Permisos de Aplicación no verificada", es mandatorio rediseñar la capa de autenticación frontend implementando el SDK de **Google Identity Services (Botón de Iniciar Sesión con Google)** en lugar de depender de `Session.getActiveUser().getEmail()` en modo `USER_DEPLOYING`.
- **[DEUDA TÉCNICA - CONFIG]:** Se descubrió que la base de datos de configuraciones aún utiliza `ENV_CONFIG` como fallback duro. La refactorización para centralizar todo en `APP_SECURITY_CONFIG` y `Global_Config.js` debe completarse en futuros mantenimientos.
