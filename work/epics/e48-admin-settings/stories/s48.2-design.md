# Design S48.2: Dynamic SSO Domain Configuration

## 1. Context & Motivation
La aplicación actualmente restringe el acceso de los usuarios comparando sus dominios de correo electrónico contra una lista estática (ej. `@coppel.com`, `@bancoppel.com`) definida en el archivo de despliegue `environments/Config.*.js` y procesada por `API_Auth.js`. Para escalar el acceso a consultoras externas sin requerir intervención de desarrollo y redespliegues continuos, se requiere que la administración pueda configurar dinámicamente estos dominios permitidos desde el Schema Studio UI.

## 2. Architecture

### 2.1 Backend (Persistence & Security)
- **Capa de Persistencia:** Aprovecharemos el `PropertiesService.getScriptProperties()` existente para almacenar una nueva propiedad llamada `APP_SECURITY_CONFIG`.
- **Estructura del Dato:** Un objeto JSON simple: `{ allowedDomains: string[] }`.
- **Endpoint:** Ampliaremos el `API_Admin.js` añadiendo la función `API_Admin_SaveSecurityConfig(payload)` validada por el control ABAC que verifica el nivel de administrador.
- **Autorización (API_Auth.js):** 
  - La función `getUserIdentity` recuperará la propiedad `APP_SECURITY_CONFIG` al vuelo.
  - Si la propiedad existe, validará que el correo finalice con cualquiera de los dominios proporcionados.
  - Si la propiedad falla o no existe, hará fallback a `CONFIG.ALLOWED_DOMAINS` o al string `ENV_CONFIG`.

### 2.2 Frontend (Schema Studio UI)
- **Ubicación:** Modificaremos la pestaña "Branding" añadida en S48.1, renombrándola conceptualmente a "Global Config" o simplemente añadiendo una sección de "Control de Acceso SSO".
- **Componente Visual:** Un textarea o input de texto (`id="input-security-domains"`) donde el administrador pueda pegar dominios separados por coma (ej. `@coppel.com, @agencia.com`).
- **Controlador:** Se añadirá `saveSecurityConfig()` a `window.SchemaStudio` para sanitizar (trim, toLowerCase, filtrar vacíos) y enviarlo al backend mediante `google.script.run`.

## 3. Data Flow
1. **Lectura (SSO Auth):**
   - El usuario abre la Web App -> Se dispara `doGet()`.
   - El sistema solicita `API_Auth.getUserIdentity()`.
   - `getUserIdentity` lee `PropertiesService`. Si encuentra `APP_SECURITY_CONFIG`, toma el array de `allowedDomains`. 
   - Retorna la identidad verificada. Si es rechazada, la app carga el módulo de `Auth_UI.html` (Vista de Denegado).

2. **Escritura (Admin):**
   - El Super Admin ingresa a Schema Studio -> Pestaña Branding/Security.
   - Modifica el string de dominios: `@coppel.com,@bancoppel.com,@nueva.com`.
   - Hace clic en Guardar -> El controlador JS sanitiza: `['@coppel.com', '@bancoppel.com', '@nueva.com']`.
   - Petición a `API_Admin_SaveSecurityConfig(payload)`.
   - Guardado en `PropertiesService`. Retorna éxito.

## 4. Alternatives Considered
1. **Guardar los dominios en Google Sheets (DB):** Descartado. Sumaría 1500-2500ms de latencia a cada carga de página solo para validar el usuario inicial. `PropertiesService` es sincrónico y responde en menos de 50ms.
2. **Utilizar ABAC Rules para dominios:** Descartado. ABAC controla permisos internos (roles/recursos), pero SSO es una barrera perimetral. Si no pasa la barrera SSO, el usuario ni siquiera debe cargar la instancia del sistema.

## 5. Security & Risk Mitigation
- **Riesgo:** El administrador borra accidentalmente todos los dominios o guarda un formato malformado.
- **Mitigación Frontend:** El cliente JS forzará siempre que exista al menos un dominio válido. Si el array resultante queda vacío, se bloqueará la operación.
- **Mitigación Backend:** `API_Auth.js` estará envuelto en un `try/catch`. Si falla la lectura, recurrirá al fallback pre-compilado en `environments/Config.*.js`.
