# Story Design: S48.4 - Autorización OAuth2 (3-Legged) para Workspace Multi-Dominio

## Problem & Value
**Problem**: Actualmente la API interna de `AdminDirectory` sólo resuelve los correos que pertenecen al dominio principal (donde el script fue publicado) o dominios previamente configurados a nivel Workspace. Los dominios secundarios fallan o requieren cuentas de servicio onerosas de configurar.
**Value**: Implementar un flujo "3-Legged OAuth2" (Google Sign-In) permitirá que un administrador de cualquier dominio secundario autorice a la aplicación Taxonomia para consultar su directorio. Esto centraliza la funcionalidad sin forzar a los administradores de TI a manejar configuraciones técnicas complejas.

## Approach
1. **Librería OAuth2**: Inyectar en `appsscript.json` la dependencia a la librería de Google Apps Script `OAuth2`.
2. **Servicio OAuth2 (`Auth_OAuth2.js`)**: Crear un módulo en el backend encargado de configurar el servicio (client ID, secret, scopes) y manejar el flujo de autorización y callback.
3. **Puntos de Integración HTTP (`Code.js`)**: Modificar la función `doGet(e)` para enrutar el callback si recibe parámetros OAuth (`e.parameter.code`), interceptando la navegación estándar.
4. **Almacenamiento**: El servicio OAuth utilizará `PropertiesService.getScriptProperties()` para almacenar de forma persistente los Refresh Tokens obtenidos, serializados por prefijo de dominio (ej: `OAUTH_TOKEN_@dominio.com`).
5. **Interceptación de Búsquedas (`Engine_Workspace.js`)**: Modificar la lógica actual que asume acceso directo vía `AdminDirectory`. Si el dominio pertenece al grupo autorizado externamente, se extraerá el Token de acceso y se consultará utilizando `UrlFetchApp` sobre la URL HTTP de la API de Directorio, parseando los DTOs igual que el flujo nativo.
6. **Frontend (`Schema_Studio_UI.html`)**: Activar el botón de "Conectar Dominio" generando el URL de autorización y manejando la tabla de dominios ya enlazados.

## Architecture Decisions
- **Uso de Librería Oficial**: Evitamos escribir y mantener a mano el engorroso intercambio de Authorization Codes por Access y Refresh Tokens y la lógica de validación de estado.
- **Identificación de Dominio Transparente**: Al recibir el callback, el sistema realizará una petición a la API de UserInfo para identificar a qué dominio pertenece el usuario que acaba de conceder los permisos, y guardará el token de Workspace con esa llave (ej. `@midominio.com`).
- **Data Mutation Strategy (Fail-Open)**: Si `UrlFetchApp` falla por token expirado/revocado, el sistema atrapará el error 401 y retornará el DTO básico igual que si el dominio no existiera, permitiendo la creación manual de la Persona sin romper el flujo principal (PAT-E-523).

## Concrete Examples

**Ejemplo 1: URL de Autorización (Frontend)**
```javascript
// El botón "Conectar Dominio" hace un GET:
window.DataAPI.call('Auth_GetWorkspaceAuthUrl').then(url => {
   // URL esperada: https://accounts.google.com/o/oauth2/auth?client_id=...&redirect_uri=...&scope=admin.directory.user.readonly
   window.open(url, '_blank');
});
```

**Ejemplo 2: Interceptación en Code.js**
```javascript
function doGet(e) {
  // Si detectamos parámetros OAuth
  if (e.parameter && e.parameter.code && e.parameter.state) {
    return Auth_HandleOAuthCallback(e);
  }
  // ... flujo de UI normal
}
```

**Ejemplo 3: Consulta Transparente en Engine_Workspace.js**
```javascript

  var dominio = queryEmail.substring(queryEmail.indexOf('@'));
  var token = Auth_GetTokenForDomain(dominio);
  
  if (token) {
    // Modo OAuth2 Externo
    var res = UrlFetchApp.fetch('https://admin.googleapis.com/admin/directory/v1/users/' + encodeURIComponent(queryEmail), {
      headers: { 'Authorization': 'Bearer ' + token }
    });
    var data = JSON.parse(res.getContentText());

    // Modo Nativo (Dominio principal)
    var u = AdminDirectory.Users.get(queryEmail);

  }
}
```

## Acceptance Criteria
- **MUST**: `Code.js` debe detectar la ruta de OAuth callback y delegar a `Auth_OAuth2.js`.
- **MUST**: `Auth_OAuth2.js` debe poder generar la URL de login y completar el intercambio de token, almacenándolo por dominio.
- **MUST**: El Frontend debe habilitar el botón "Conectar Dominio".
- **MUST**: `Engine_Workspace.js` debe intentar el aprovisionamiento usando `UrlFetchApp` para dominios que tengan tokens almacenados.
- **MUST**: Mantener el soporte intacto para el dominio principal (usando `AdminDirectory`).
