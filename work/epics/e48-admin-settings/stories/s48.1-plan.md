# Plan S48.1: Admin Configuration Tab for Custom Branding

**Story:** S48.1
**Size:** S (Small)
**Date:** 2026-04-30

## 1. Task Breakdown

### Task 1: Backend API (API_Admin.js)
- **Description:** Crear el endpoint para persistir la configuración en `PropertiesService`.
- **Files to modify:** `src/API_Admin.js`
- **TDD / Verification:** Al no tener un framework de unit test activo en GAS puro, la verificación es revisar la sintaxis (Lint) y que no se rompan las dependencias.
- **Size:** XS
- **Dependencies:** None

### Task 2: Core Routing (Code.js)
- **Description:** Modificar `doGet(e)` para leer la propiedad `APP_BRANDING_CONFIG` e inyectar el favicon y título usando el HtmlOutput.
- **Files to modify:** `src/Code.js`
- **TDD / Verification:** Revisión de sintaxis; verificar que el try-catch protege contra configuraciones corruptas.
- **Size:** XS
- **Dependencies:** None (Independiente de la Tarea 1, pero usa la misma key).

### Task 3: UI Frontend (Governance_Admin_UI.html)
- **Description:** Agregar la pestaña "Configuración", construir el formulario HTML/CSS, e invocar el backend usando `google.script.run.API_Admin_SaveBrandingConfig()`.
- **Files to modify:** `src/Governance_Admin_UI.html`
- **TDD / Verification:** Validar AST / HTML Lint (mediante `npm run deploy:dev:auto`).
- **Size:** S
- **Dependencies:** Tarea 1 (Requiere que el backend exista para no arrojar error al guardar).

### Task 4: Manual Integration Test & Deployment
- **Description:** Ejecutar despliegue a DEV (`npm run deploy:dev:auto`) y verificar de extremo a extremo (E2E) en el entorno de Apps Script.
- **Files:** N/A
- **Verification:** 
  1. Ingresar al panel de admin y guardar un nuevo título/ícono.
  2. Recargar y verificar que el navegador muestra el nuevo favicon y title.
- **Size:** XS
- **Dependencies:** Tarea 1, Tarea 2, Tarea 3.

## 2. Execution Order & Rationale
**Orden:** T1 -> T2 -> T3 -> T4.
**Rationale:** Es el clásico "Backend -> Integración -> Frontend". Primero aseguramos el punto de guardado (T1), luego cómo lo va a leer el sistema principal al cargar (T2), luego le damos la interfaz visual al usuario para modificarlo (T3), y finalmente probamos (T4). No hay riesgos cruzados al ser altamente secuencial.

## 3. Risks and Mitigations
- **Riesgo:** Un JSON malformado en PropertiesService podría bloquear el `doGet`.
- **Mitigación:** Se implementará un bloque estricto `try/catch` con un fallback definido a los valores seguros corporativos si la lectura o parseo falla.
