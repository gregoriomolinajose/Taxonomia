## What went well
The integration of the singleton pattern for `AuthManager` was straightforward, and applying strict URL sanitization for the Avatar XSS vulnerability was completed without affecting existing functionality. The team quickly resolved domain leakage by implementing a generic error handler for client-facing exceptions.

## What to improve
We had issues with test runner collisions (Jest and Vitest both trying to execute all test files). We should separate the configurations and exclude E2E Playwright tests from the unit test runners explicitly.

## Heutagogical Checkpoint

**1. What did you learn?**
I learned the importance of singleton state management (`_initialized` flag) during application bootstrap to prevent race conditions and duplicate API calls in a Google Apps Script/Ionic frontend environment. I also reinforced my knowledge of XSS mitigation by manually sanitizing Avatar URLs before they are bound to the DOM.

**2. What would you change about the process?**
I would add a requirement for automated network traffic assertions (e.g., asserting that `DataAPI.call` is only triggered once) during the `RED` phase of TDD to ensure we don't regress on initialization duplicate calls.

**3. Are there improvements for the framework?**
Yes, the test environments (Vitest vs Jest vs Playwright) need strict boundary definitions in their respective config files to prevent overlapping execution, which causes false-positive failures during the CI/review phase.

**4. What are you more capable of now?**
I am more capable of securing the application against minor but critical vulnerabilities (like domain leakage in error messages) while preserving the developer experience by logging the full errors server-side.

## Improvements Applied

- Fixed the mock environment for `AuthManager.test.js` to properly mock Ionic UI elements like `ion-loading` with a `dismiss` method.
