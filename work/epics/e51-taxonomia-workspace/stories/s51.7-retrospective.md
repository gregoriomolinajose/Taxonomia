# S51.7: Contextual Hierarchy Builder Retrospective

## Outcomes
- **Status:** Done
- **Deliverables:**
  - Added `id_unidad_negocio` (Unidad_Negocio), `id_portafolio` (Portafolio), and `grupos_productos` (Grupo_Productos) to the `Taxonomia` schema.
  - Set `workspaceMode: true` on these fields so that relationships are contextualized.
  - Implemented the `dynamicParentField` metadata.
  - Enhanced `Engine_DB.js` to process dynamic parent ID bindings, falling back gracefully to string resolution and parsing the array representations appropriately.
  - Upgraded `UI_Component_RelationBuilder.client.js` to effectively hydrate elements with `workspaceMode` regardless of parent ID fixed bindings.

## Discoveries & Learnings
- **Metadata-Driven ETL Validation**: The use of `dynamicParentField` allowed us to expand the ETL engine seamlessly. Modifying the generic data structures enables the UI to remain agnostic of the actual field bindings, relying strictly on configuration rules to build tripartite edges.
- **Data Normalization Pitfalls**: We discovered that fields like `searchable_multi` flatten relational selections. The use of single selections for parent layers (`id_unidad_negocio`, `id_portafolio`) proved vital for strict graph cardinality, preventing data corruption within array representation of foreign keys.

## Process Improvements
- Continue adhering to metadata-driven architectures to avoid ad-hoc hardcoding in validation or database persistence layers.
- Maintain a strict topological representation when evaluating dynamic arrays (searchable multi vs select single).
