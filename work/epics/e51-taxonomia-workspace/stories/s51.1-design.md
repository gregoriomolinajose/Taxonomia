# Story Design: S51.1 Schema Engine & Workspace Mode Definition

## What & Why
**Problema:** Los componentes de UI necesitan una señal para saber si una relación debe guardarse como bipartita normal (`Taxonomia -> Nodo`) o tripartita en Workspace Mode (`Rol -> Nodo` con `contexto = Taxonomia`).
**Valor:** Inyectar esta metadata en el `Schema_Engine` permite que la lógica sea guiada por la configuración, evitando hardcodear la lógica directamente en los constructores de React/JS.

## Approach
*   **Componentes afectados:** `Schema_Engine.js` (Modify).
*   **Enfoque:** Agregaremos `workspaceMode: true` y el respectivo `fixedParentId` (ej. "ROLE-16") a los 3 campos creados anteriormente (`head_of_technology`, `technology_manager`, `technical_lead`).

## Examples

**Configuración Esperada en Schema_Engine:**
```javascript
{ 
  name: "head_of_technology", 
  type: "relation", 
  relationType: "hijo", 
  targetEntity: "Persona", 
  graphEntity: "Sys_Graph_Edges", 
  // ...
  workspaceMode: true,           // NUEVO
  fixedParentId: "ROLE-16",      // NUEVO: Head of Technology
  graphEdgeType: "PERSONA_ROL"   // AJUSTADO: La arista real que modelamos
}
```
*Nota: Actualizaremos `graphEdgeType` a `PERSONA_ROL` porque esa es la arista arquitectónica real entre un Rol y una Persona, apoyándonos en que el `contexto_id` garantizará la separación entre taxonomías.*

## Acceptance Criteria
*   **MUST:** Los 3 campos de roles técnicos incluyen la bandera `workspaceMode: true`.
*   **MUST:** Cada campo incluye su `fixedParentId` correcto apuntando a la entidad Rol (ROLE-16, ROLE-17, ROLE-10).
*   **MUST:** El `graphEdgeType` de los 3 campos es cambiado a `PERSONA_ROL` para mantener coherencia ontológica.
