# Design: S44.18 Optimización de Rendimiento en Workspace Sync

## What & Why
- **Problem**: El sincronizador de Workspace carga el 100% de la base de datos de empleados a memoria RAM para buscar faltantes, y guarda los datos de forma iterativa 1 por 1, sufriendo del Anti-Patrón de Base de Datos N+1 que dispara la latencia e impacta el límite de cuota de Google Apps Script.
- **Value**: Reducir el tiempo de ejecución en un 90% (de ~15s a ~1.5s por lote de 50), y asegurar que el sistema no colapse por memoria insuficiente (OOM) a medida que crece el tamaño de la plantilla, logrando una sincronización verdaderamente asíncrona, robusta y escalable.

## Approach
1. **Filtrado Server-Side Minimalista (O(1) Memoria)**: 
   - [MODIFY] `Adapter_Sheets.js`: Ampliar `list()` agregando un parámetro opcional `rawFilterFn` (callback lambda) que permita filtrar la matriz bidimensional original (celdas puras de `getDataRange().getValues()`) *antes* de mapearlas a pesados objetos de JavaScript. Esto evita construir un motor de consultas SQL complejo (YAGNI).
2. **Refactorización Topológica Pura (Extracción SCD-2)**:
   - [NEW] `Topology_Strategies.js` (o usar uno existente): Extraer la lógica matemática de dimensionado lento (cierre de vieja arista y apertura de nueva) desde `Engine_DB.orchestrateNestedSave` hacia un método estático sin estado: `Topology_Strategies.calculateSCD2Transitions()`.
3. **Escritura Masiva Topológica (Bulk Insert O(1))**: 
   - [MODIFY] `Job_WorkspaceSync.js`: Eliminar el iterador individual. Ahora el proceso consumirá `Topology_Strategies.calculateSCD2Transitions` para ensamblar el historial SCD-2 de los 50 empleados en RAM, y luego enviará un array masivo puramente plano a `Engine_DB.upsertBatch` para Personas y otro para `Sys_Graph_Edges`. Todo se graba en 2 operaciones de red.

## Value Preservation Gate (PAT-E-572)
El conocimiento de dominio crítico aquí es la integridad relacional de Grafos SCD-2 (Manejo de versiones e historial en las aristas topológicas). El `orchestrateNestedSave` manejaba esto. Para no perder el valor de SCD-2, la nueva lógica en lote (Bulk) *debe* construir las aristas (cerrar las viejas `es_version_actual = false`, crear las nuevas) en la memoria RAM antes de enviar el array definitivo al `upsertBatch` de `Sys_Graph_Edges`.

## Examples

### 1. Invocación de Capa (Antes vs Después)

**❌ Antes (Lento, O(N)):**
```javascript
var personas = Adapter_Sheets.list('Persona'); // Carga 10,000 registros
var candidatos = personas.filter(p => !p.workspace_sync_status);

candidatos.forEach(p => {
    // 50 peticiones de red
    Engine_DB.orchestrateNestedSave('Persona', p);
});
```

**✅ Después (Rápido, O(1) con Callback Crudo):**
```javascript
// Filtro crudo que opera sobre el arreglo nativo 2D antes de instanciar objetos
const rawFilter = (rowArray, headerMap) => {
    const status = rowArray[headerMap['workspace_sync_status']];
    return !status || status === 'pending' || status === 'failed';
};
var candidatos = Adapter_Sheets.list('Persona', { rawFilterFn: rawFilter, limit: 50 });

// Generación de Aristas SCD-2 en memoria (Lógica Extraída)
var payloadEdges = Topology_Strategies.calculateSCD2Transitions(oldEdges, newEdges);

// Se escribe todo el lote en 2 llamadas
Engine_DB.upsertBatch('Persona', candidatosHydratados);
Engine_DB.upsertBatch('Sys_Graph_Edges', payloadEdges);
```

## Acceptance Criteria
- **MUST**: `Job_WorkspaceSync.js` no debe ejecutar `Adapter_Sheets.list` completo sin restricciones. Debe descargar solo el lote filtrado.
- **MUST**: La base de datos debe ser mutada usando llamadas en masa (bulk write) en lugar del iterador individual O(N).
- **MUST**: Las relaciones de jerarquía (`Sys_Graph_Edges`) deben forjarse extrayendo la lógica a `Topology_Strategies` para no duplicar código con `orchestrateNestedSave`.
- **MUST NOT**: Modificar el comportamiento de UI ni requerir intervención manual; esto es puramente optimización backend.
