# Architecture Review: S44.7 Reorganización Estructural Persona

**Target:** Epic E44 / Story S44.7
**Type:** System Architecture Review (SAR)

## 1. Contexto Teórico

La S44.7 propone reorganizar el formulario gigante de Entidad `Persona` dividiéndolo en agrupaciones semánticas (Datos Personales, Empresariales, Contacto, Agilidad, etc.). 
Para lograr esto sin alterar el motor troncal, se ha introducido un patrón de **Form DSL Extension**, inyectando campos virtuales `type: "divider"` directamente dentro del arreglo de `fields` en `APP_SCHEMAS`.

## 2. Evaluación Heurística (Beck's Four Rules)

### ✅ Rule 1: Pasa las pruebas (Funcionalidad Aislada)
El inyector `UI_Factory.buildDivider` ya existe y ha sido incorporado para procesar esta bandera y escupir un contenedor visual emparejado con ion-icons. Adicionalmente, el ETL y los adaptadores de base de datos (`Adapter_Sheets_Provisioner.js` y `Adapter_Sheets.js`) han sido previamente provistos de exclusiones para que esta columna visual no ensucie la persistencia de columnas reales (`f.type !== 'divider'`).
**Veredicto:** Funcional.

### ⚠️ Rule 2: Revela la Intención (Semantic Purity)
**Riesgo Detectado:** El arreglo lógico `fields` debería, en estricta teoría de diseño de software, contener únicamente las propiedades del modelo de dominio. Inyectar `separator_X` mezcla las *Vistas* con los *Datos*, cometiendo el falso concepto de "Liar by Type" (Un campo que no es un campo real).
Sin embargo, `Schema_Engine.js` ya opera arquitectónicamente en Taxonomia como un Domain-Specific Language (DSL) Abstracto que comanda la GUI. Sus arreglos ya dictan layouts visuales (`width: 6`), controladores React/Stencil (`uiComponent`) y reglas ABAC explícitas. Por tanto, nuestro DSL orgánico *ya asume* responsabilidad visual integrada.
**Veredicto:** Compromiso pragmático justificado. Un motor purista exigiría un arreglo jerárquico separado (ej. `layout: [{section:'', fields:[]}]`), pero violaría el Principio 4 introduciendo "Speculative Generality".

### ✅ Rule 3: Eliminación de Duplicación
La centralización del render en `FormBuilder_Inputs.js` garantiza que estos headers divisorios obedecen globalmente a los paddings escalados universales y reaccionan al Theme Builder de la App automáticamente sin incrustar nodos huérfanos.

### ✅ Rule 4: Minimiza los Elementos (Lean Core)
Esta es la principal victoria arquitectónica. Al emular *Virtual Fields*, evitamos el desarrollo exhaustivo y destructivo de un "Layout Config Manager" dentro del motor subyacente. Inyectamos `type: 'divider'` directamente y el parser de Formularios lo pinta linealmente en O(N).

## 3. Descubrimiento Estratégico (Zero-Trust UI Layouting)

**Gestión Semántica de Permisos ABAC Acoplados:** 
Lo más destacado en el propuesto `APP_SCHEMAS.Persona` es lo siguiente:
```javascript
{ name: "separator_5", type: "divider", label: "Control de Accesos (Admin)", width: 12, abacRule: { action: 'update', target: 'Sys_Permissions' } }
```
Al inyectarle una regla formal `abacRule` al propio *Divider*, se fuerza al servidor NodeJS a eliminar estructuralmente esta etiqueta desde el Origen (Server-Side) para aquellos empleados sin rol de Admin. 
Esto previene orgánicamente que los usuarios estables vean "Títulos huérfanos sin inputs debajo de ellos", una solución sumamente brillante porque unifica nuestro motor de Vistas con el motor Zero-Trust.

## 4. Dictamen Final

**[APPROVED]**
La S44.7 se alinea directamente con una solución "Lean". Demuestra que la simplicidad (agregando un Type a la matriz de objetos) puede solventar requerimientos enormes de UI (Segmentación Topológica de Modelos Gigantes) sin bifurcar capas del frontend. 

El esquema está validado arquitectónicamente. La revisión ha concluido sin hallazgos bloqueantes.
