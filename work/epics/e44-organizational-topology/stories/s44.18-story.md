# S44.18: Optimización de Rendimiento en Workspace Sync

## User Story

**As a** system administrator
**I want** the Workspace Sync job to execute in O(1) bulk operations instead of O(N) iterative loops
**So that** the sync process scales linearly and completes in a fraction of the time, avoiding unnecessary memory consumption and excessive network latency against Google Sheets as the employee database grows.

## Acceptance Criteria

- **MUST**: Update `Job_WorkspaceSync` to query the database iteratively using Server-Side filtering (only requesting rows where `workspace_sync_status` is pending/failed) rather than loading the entire `Persona` table into memory.
- **MUST**: Implement a Bulk Edge Insertion mechanism via `Engine_DB.upsertBatch` or a similar bulk API, eliminating the `forEach` loop that currently calls `orchestrateNestedSave` 50 individual times.
- **MUST**: Ensure that the topological relationships (`Sys_Graph_Edges`) created in bulk preserve SCD-2 (Slowly Changing Dimensions) integrity just as the iterative save did.
- **MUST NOT**: Exceed Google Apps Script's 6-minute timeout or 50MB memory limit during execution, even with 5,000+ records in the `Persona` database.

## Context

El Job `runWorkspaceSyncJob` actualmente es robusto contra caídas, pero adolece de un Anti-Patrón N+1 de Base de Datos. Para saber quiénes necesitan sincronización, lee el 100% de la tabla `Persona` a la memoria RAM. Luego, para guardar las 50 actualizaciones y crear sus relaciones jerárquicas en el Grafo (Cargos), itera 50 veces haciendo 50 peticiones de red individuales (escrituras) mediante `orchestrateNestedSave`. 

Se busca optimizar ambos flujos de datos: Filtrar en origen (O(1) lectura parcial) y guardar en masa (Bulk Insert O(1) escritura) para asegurar la viabilidad técnica del producto a largo plazo.
