## Architecture Review: S44.17 (scope: story)

### Contexto
El objetivo de la historia S44.17 es inyectar la lógica de Workspace Sync dentro del pipeline de Carga Masiva (ETL) para la entidad `Persona`, de manera que los Cargos se aprovisionen automáticamente y las relaciones se guarden en `Sys_Graph_Edges`.

### Critical (fix before merge)
* **H9 (Semantic Duplication) / H10 (Pattern Duplication):** 
  * *Ubicación:* `Engine_ETL.js` (Líneas 194-240) vs `Job_WorkspaceSync.js` (Líneas 100-150).
  * *Observación:* Actualmente `Engine_ETL` tiene un "Interceptor" quemado para `Persona` que crea `Cargos` falsos/temporales ("Por definir") y NO consulta el Workspace, mientras que `Job_WorkspaceSync.js` sí consulta Workspace y luego llama a `Engine_DB.orchestrateNestedSave`. Si metemos la lógica de Workspace en `Engine_ETL` como pide la historia de forma literal, duplicaremos el bucle de hidratación.
  * *Solución Propuesta:* Se debe centralizar la lógica de resolución en `Engine_Workspace.js` o delegar desde la capa `API_Universal.js` para invocar a `Job_WorkspaceSync` de manera encadenada (en lotes de 50) si se detecta que el payload viene hacia la entidad `Persona`.

* **H14 (Coupling Direction):** 
  * *Observación:* `Engine_ETL.js` (Core estable de ingesta) no debería importar ni acoplarse fuertemente a `resolverDirectorioWorkspace` (Módulo volátil).
  * *Solución Propuesta:* El acoplamiento debe hacerse en la capa de coordinación (`API_Universal.js` o `Controller_Action.js`), interceptando el payload ANTES o DESPUÉS del guardado masivo normal.

### Recommended (simplify before next cycle)
* **Rendimiento de Escritura (OOM / Timeouts):**
  * *Observación:* La Carga Masiva utiliza `Engine_DB.upsertBatch()` para insertar 1000 registros en ~2 segundos de forma plana. `Job_WorkspaceSync.js` utiliza iteraciones de `Engine_DB.orchestrateNestedSave()` que es muy costoso porque calcula grafos recursivos, por lo cual tiene un límite de 50 lotes (15s máximo).
  * *Solución Propuesta:* Si ejecutamos recursivamente `orchestrateNestedSave` para un CSV de 500 personas en la carga masiva, **Google Apps Script lanzará timeout**. Debemos enviar la tarea a Background (Time-driven trigger) o manejarla con paginación desde el cliente (UI_ETL_Modal).

### Verdict
- [ ] PASS 
- [ ] PASS WITH QUESTIONS 
- [x] SIMPLIFY

> **Conclusión de Arquitectura:** Integrar Workspace Sync directamente de forma síncrona dentro del webhook de ETL de Google Apps Script es **inviable y de altísimo riesgo** para el rendimiento (Timeouts masivos de >6 minutos si el CSV es muy grande). 
> **Recomendación Estratégica:** En lugar de recargar el backend, debemos hacer que el cliente (`UI_ETL_Modal.html`) dispare asíncronamente `DataAPI.call('runWorkspaceSyncJob')` *inmediatamente después* de recibir el `status: success` de la ingesta de Personas, mostrando una barra de progreso que diga *"Configurando Topología Workspace..."* antes de cerrar el modal. Esto re-utiliza código sin tocar el backend, evita timeouts (paginación segura) y no viola las capas de arquitectura.
