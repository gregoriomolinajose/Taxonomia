## Architecture Review: S44.18 (scope: story design)

### Critical (fix before merge)
*Ninguno.* El diseño conceptual propuesto ataca directamente los cuellos de botella reales sin requerir refactorizaciones masivas o destructivas.

### Recommended (simplify before next cycle)
* **H7 (Abstraction-to-LOC Ratio) en `Adapter_Sheets.query()`**:
  El diseño propone crear un método `query()` en el adaptador para filtrar *Server-Side*. Sin embargo, Google Sheets (`SpreadsheetApp`) no posee un motor de consultas SQL nativo; la única forma de leer es `sheet.getDataRange().getValues()`, lo cual inevitablemente carga toda la matriz bidimensional a memoria RAM. Construir un mini-ORM o constructor de Queries solo para este caso sería sobre-ingeniería (Violación de YAGNI - Beck Rule 4).
  *Simplificación concreta*: En lugar de crear un método de `query` genérico, simplemente modificar `Adapter_Sheets.list` para aceptar una función lambda de filtrado crudo (sobre el array 2D original por índice de columna) antes de realizar el costoso casteo a Objetos de JavaScript. Esto resuelve el problema de RAM sin inventar una nueva abstracción.

### Questions (require human judgment)
* **H10 (Pattern Duplication)**: La lógica de SCD-2 (Cierre temporal de aristas obsoletas y creación de nuevas) actualmente vive de forma fuertemente acoplada dentro de `Engine_DB.orchestrateNestedSave`. Si calculamos los cierres topológicos de 50 registros en memoria (RAM) dentro del Job para pasárselos planos a `upsertBatch`, ¿estamos duplicando la lógica de dimensionado lento que ya existe en `orchestrateNestedSave`? 
  *Alternativa*: ¿Debería extraerse la lógica SCD-2 a una función de utilidad puramente funcional (ej. `Topology_Strategies.calculateSCD2Transitions(oldGraph, newGraph)`) para que tanto `orchestrateNestedSave` como el proceso Bulk puedan consumirla sin duplicar reglas de negocio?

### Observations (patterns noted)
* **H6 (Indirection Depth) evitado con éxito**: La decisión explícita (D1) en el diseño de *no* hacer que `upsertBatch` sea recursivo/relacional mantiene las capas limpias. `upsertBatch` seguirá siendo estúpidamente simple (escribe un array plano en una hoja plana), respetando KISS (Beck Rule 2). Toda la complejidad topológica se resolverá en la capa superior antes de invocar la escritura.
